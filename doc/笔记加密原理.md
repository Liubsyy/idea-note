# 笔记加密原理

> 这篇文档面向使用 Idea Note 的普通用户，按“先看到结果，再理解原因”的顺序解释笔记加密。
>
> 第一次阅读建议从头开始。文中的技术名称都会先用中文说明，再给出英文名或代码名，不需要预先了解密码学。
---

## 1. 加密一段笔记后，究竟发生了什么

假设笔记中原来有一句话：

```text
服务器口令是 correct-horse-battery-staple
```

选中它并执行加密后，Markdown 文件里不再保存这句明文，而会保存类似下面的内容：

````markdown
```secret {v=1, key=k1, id=b0e08703dbc4ccbc2}
9EhLEDOBweDbCawtEHFT3ZmBbtKIPlSPLuTU6Q7v_0Cq6fPVfoib94BTnHFhhNALpF1mcET4HQ
```
````

这段看不懂的字符就是加密结果。它会进入磁盘文件、自动保存和 Git 历史。原来的文字只会在用户主动解密时出现在 Idea Note 的加密内容编辑器中。

从用户角度看，完整过程只有两条。

加密：

```text
明文
  ↓ 使用工作区主密钥加密
密文
  ↓ 转成适合写入 Markdown 的字符
secret 加密块或行内加密内容
```

解密：

```text
secret 中保存的字符
  ↓ 还原成密文
密文
  ↓ 使用同一把工作区主密钥解密
明文
```

后面的章节就是把这两条流程逐步展开。

## 2. 为什么中间要经过好几次转换

加密算法不直接处理“文字”，Markdown 也不适合直接保存任意二进制数据。因此一段内容从明文到文件，要经过三个步骤。

### 2.1 第一步：把文字转成字节

用户输入的是文字，例如：

```text
你好，Idea Note
```

加密算法接收的是字节。Idea Note 使用 UTF-8，把文字转换成一串确定的字节：

```text
明文文字
  ↓ UTF-8
明文字节
```

UTF-8 不是加密，只是规定每个字符如何表示成数字。没有密钥也可以随时还原。

### 2.2 第二步：把明文字节加密

Idea Note 使用 XChaCha20-Poly1305。它接收明文字节和密钥，产生一个二进制加密包。

这个加密包由三部分组成：

```text
24 字节随机数 │ 加密后的内容 │ 16 字节防篡改校验值
```

对应的代码和密码学名称是：

| 中文含义 | 本文统一名称 | 长度 | 作用 |
| --- | --- | --- | --- |
| 随机数 | `nonce` | 固定 24 字节 | 让同一段明文每次加密都得到不同结果 |
| 加密后的内容 | `ciphertext` | 与明文字节数相同 | 真正被隐藏的正文 |
| 防篡改校验值 | `tag` | 固定 16 字节 | 判断密钥、密文和相关信息是否正确 |

本文后面始终使用 `nonce`、`ciphertext` 和 `tag`，长度只在需要计算时单独说明，不再拼进名称。

所以后文出现：

```text
nonce ‖ ciphertext ‖ tag
```

只是在简写：

```text
24 字节随机数 ‖ 加密后的内容 ‖ 16 字节防篡改校验值
```

其中 `‖` 表示“按顺序拼接”，不是数学运算。

防篡改校验值不是普通文件校验和。它依赖秘密密钥，攻击者修改密文后无法自己生成一个有效的新校验值。校验失败时，程序不会返回任何明文。

### 2.3 第三步：把二进制加密包转成文本

上一步得到的是二进制字节，直接放进 Markdown 可能包含不可显示字符。Idea Note 因此再使用 base64url，把二进制加密包转换成普通文本：

```text
二进制加密包
  ↓ base64url
由字母、数字、- 和 _ 组成的文本
```

base64url 也不是加密。它只负责改变表示方式，任何人都可以把它还原成二进制加密包；但没有密钥，仍然无法把包里的密文解开。

### 2.4 三步连起来

现在可以得到第一条完整且没有省略的流程：

```text
用户输入的文字
  ↓ UTF-8：文字转字节
明文字节
  ↓ XChaCha20-Poly1305：真正的加密
24 字节随机数 ‖ 加密后的内容 ‖ 16 字节防篡改校验值
  ↓ base64url：二进制转文本
写入 Markdown 的 secret 内容
```

只需记住：

- UTF-8 在加密前处理明文；
- XChaCha20-Poly1305 才是真正的加密；
- base64url 在加密后处理密文。

## 3. 加密需要的密钥从哪里来

理解了内容如何变化，下一步是回答：XChaCha20-Poly1305 使用的密钥是什么？

### 3.1 每个工作区有一把随机主密钥

Idea Note 第一次设置加密时，会随机生成一把 32 字节密钥。它负责加密这个工作区里的所有 secret 内容。

这把密钥叫作“工作区主密钥”，英文是 Master Key，代码中简称 **MK**。

```text
工作区主密钥（MK）
  ├ 加密 secret A
  ├ 加密 secret B
  └ 加密 secret C
```

MK 是操作系统随机生成的，不是从口令直接算出来的。它也不会以明文形式写进文件。

### 3.2 口令的职责是保护 MK

如果 MK 不能明文保存，应用重启后又该怎样找回它？答案是用用户口令把 MK 加密保存。

但用户口令长度不固定，也可能很容易猜，不能直接当作 XChaCha20-Poly1305 的 32 字节密钥。Idea Note 先用 Argon2id 把口令派生成一把固定长度的密钥：

```text
用户口令
  ↓ Argon2id
32 字节密钥
```

这把只用于保护 MK 的密钥叫作“密钥加密密钥”，英文是 Key Encryption Key，代码中简称 **KEK**。

然后使用 KEK 加密 MK：

```text
MK
  ↓ 使用 KEK 加密
被包裹保存的 MK
```

“包裹”只是为了区分用途：这里加密的是另一把密钥，而不是笔记正文。底层仍然使用 XChaCha20-Poly1305。

### 3.3 为什么不直接用口令加密笔记

把口令和 MK 分成两层有一个直接好处：修改口令时，不需要重新加密所有笔记。

```text
旧口令 → 取得同一把 MK → 用新口令重新包裹 MK
```

笔记始终由同一把 MK 加密，所以修改口令只改变一个很小的密钥文件，不会产生整个仓库的密文改动。

## 4. `vault.json`、slot 和恢复码

### 4.1 `vault.json` 是工作区的密钥文件

被口令保护后的 MK 保存在：

```text
<工作区>/.ideanote/vault.json
```

这个文件不保存以下内容：

- 口令明文；
- 恢复码明文；
- KEK 明文；
- MK 明文。

它保存的是“如何从输入派生 KEK”以及“被 KEK 加密后的 MK”。

### 4.2 slot 是一份 MK 的加密信封

同一把 MK 可以分别用口令和恢复码保护。`vault.json` 把每一份记录称为一个 slot，可以把它理解成一只加密信封：

```text
口令 slot s1
  └ 用口令派生的 KEK 包裹同一把 MK

恢复码 slot s2
  └ 用恢复码派生的 KEK 包裹同一把 MK
```

当前初始化会创建两个 slot：

| slot | 用户输入 | 解开后得到什么 |
| --- | --- | --- |
| `s1` | 主口令 | 工作区 MK |
| `s2` | 恢复码 | 同一把工作区 MK |

所以“解密 vault slot”不是解密笔记，而是：

```text
使用输入值派生 KEK
  ↓
使用 KEK 解开 slot 中被包裹的 MK
  ↓
取得工作区 MK
```

### 4.3 文件结构

下面只展示理解原理所需的字段：

```json
{
  "version": 1,
  "activeKeyId": "k1",
  "slots": [
    {
      "id": "s1",
      "type": "password",
      "label": "主口令",
      "keyId": "k1",
      "kdf": {
        "alg": "argon2id",
        "m": 65536,
        "t": 3,
        "p": 1,
        "salt": "<随机盐的 base64 文本>"
      },
      "wrapped": "<被口令 KEK 加密后的 MK>",
      "createdAt": 1756500000000
    },
    {
      "id": "s2",
      "type": "recovery",
      "label": "恢复码",
      "keyId": "k1",
      "kdf": { "...": "恢复码自己的参数和随机盐" },
      "wrapped": "<被恢复码 KEK 加密后的同一把 MK>",
      "createdAt": 1756500000000
    }
  ]
}
```

`salt` 是“随机盐”：一段公开的随机输入，让相同口令在不同 slot 中也得到不同 KEK。`m`、`t`、`p` 是 Argon2id 的计算成本参数，第 6.1 节会逐项说明。`activeKeyId` 表示新内容当前使用哪一把 MK；初始化时是 `k1`，重置 MK 后会换成新的随机标识。

这里的 `wrapped` 仍然是“24 字节随机数 + 加密后的 MK + 16 字节防篡改校验值”，只是为了写进 JSON，外层使用标准 Base64，而不是笔记正文使用的 base64url。

`vault.json` 必须和笔记一起备份或提交到仓库。因为 MK 是随机生成的，丢失这个文件后，即使记得口令也无法重新算出原来的 MK。

如果文件损坏或出现非法 JSON，Idea Note 会报告错误并提示从 Git 历史恢复，不会把它当成“尚未初始化”然后覆盖。

### 4.4 恢复码

初始化时会随机生成 15 字节恢复材料，再编码成 24 个 Base32 字符，以每 6 个字符一组显示。Base32 和 Base64 一样只是把二进制数据变成容易抄写的字符，不是加密。

恢复码只显示一次。输入时不区分大小写，并忽略连字符、空格等非字母数字分隔符。

重新生成恢复码时，用户必须先用当前口令或恢复码证明能够取得 MK。新恢复码生效后，旧恢复码立即失效，笔记密文不需要改变。

同时丢失口令、恢复码或 `vault.json`，都会导致加密内容永久无法恢复。

## 5. 三条完整流程

到这里，文字、密文、MK、KEK 和 slot 都已经出现过，可以把初始化、加密和解密分别画完整。

### 5.1 第一次设置口令

```text
操作系统随机生成 32 字节 MK
  ↓
用户设置口令
  ↓ Argon2id
生成口令 KEK
  ↓ 使用 KEK 加密 MK
生成口令 slot s1
  ↓
随机生成恢复码
  ↓ Argon2id
生成恢复码 KEK
  ↓ 使用 KEK 加密同一把 MK
生成恢复码 slot s2
  ↓
把两个 slot 写入 .ideanote/vault.json
```

初始化完成后，MK 会留在 Rust 内存中，工作区进入已解锁状态。

### 5.2 加密一段笔记

```text
如果 Rust 内存中没有 MK，先输入口令或恢复码
  ↓
从 vault slot 取得 MK
  ↓
用户文字转成 UTF-8 明文字节
  ↓
使用 MK 和 XChaCha20-Poly1305 加密
  ↓
得到：24 字节随机数 + 加密后的内容 + 16 字节防篡改校验值
  ↓
使用 base64url 转成文本
  ↓
写入 Markdown 的 secret
```

### 5.3 解密一段笔记

```text
如果 Rust 内存中没有 MK，先输入口令或恢复码
  ↓ Argon2id
得到 KEK
  ↓ 使用 KEK 解开 vault slot
取得 MK
  ↓
读取 secret 中的 base64url 文本
  ↓
还原：24 字节随机数 + 加密后的内容 + 16 字节防篡改校验值
  ↓
使用 MK 校验并解密
  ↓
明文字节按 UTF-8 还原成文字
  ↓
显示在加密内容的嵌套编辑器中
```

如果 MK 仍在 Rust 内存中，第二次加密或解密可以直接使用它，不需要再次运行 Argon2id。但是否可以继续使用，还要看口令有效期，见第 8 节。

## 6. 使用的密码学算法

### 6.1 Argon2id：从口令派生 KEK

Argon2id 是密钥派生函数，不是加密算法，也没有“解密 Argon2id”这一操作。

它把任意长度的口令和一段随机盐作为输入，经过高内存、重复计算后，输出固定 32 字节 KEK：

```text
口令 + 随机盐 + 成本参数
  ↓ Argon2id
32 字节 KEK
```

当前每个 slot 保存自己的参数：

| 参数 | 当前值 | 含义 |
| --- | --- | --- |
| 算法 | Argon2id，版本字段 `0x13` | 使用的派生算法与版本 |
| `m` | `65536 KiB` | 每次派生需要约 64 MiB 内存 |
| `t` | `3` | 计算执行 3 轮 |
| `p` | `1` | 并行度为 1 |
| 盐 | 随机 16 字节 | 让相同口令在不同 slot 中派生出不同 KEK |
| 输出 | 32 字节 | 作为 XChaCha20-Poly1305 密钥 |

盐不是秘密，必须保存在 `vault.json` 中。它防止攻击者预先计算一张通用口令表，但不能把弱口令变成强口令。

项目不强制口令复杂度。Argon2id 只能提高每次猜测的成本，真正容易猜中的口令仍然可能被离线破解。

### 6.2 XChaCha20-Poly1305：加密并防止篡改

这个名称可以拆成两部分理解：

- **XChaCha20**：把明文字节变成加密后的内容，负责保密；
- **Poly1305**：生成 16 字节防篡改校验值，负责验证完整性。

两者组合成一种“带认证的加密算法”，英文简称 AEAD。它保证：只有同时拥有正确密钥、正确随机数、正确密文和正确相关信息，解密才会成功。

这里的“相关信息”是指 `v`、`key`、`id` 这类不需要隐藏、但不能被悄悄修改的属性。密码学把它称为“附加认证数据”，简称 AAD；本节先把它当作参与防篡改校验的属性，第 7 节再解释它的格式和作用。

#### XChaCha20-Poly1305 的具体参数

| 参数 | 当前实现 | 是否需要保密 | 作用 |
| --- | --- | --- | --- |
| 密钥 | 32 字节（256 位） | **是** | 包裹 MK 时使用 KEK；加密笔记时使用 MK |
| 随机数 nonce | 24 字节（192 位） | 否 | 保证同一密钥的每次加密使用不同输入 |
| 防篡改校验值 tag | 16 字节（128 位） | 否 | 验证密钥、密文和相关信息是否一致 |
| 附加认证数据 AAD | 长度可变 | 否 | 不加密，但参与 tag 校验；第 7 节详细解释 |

nonce 和 tag 都可以与密文一起公开保存。只有 32 字节密钥必须保密。

#### 加密正文时发生什么

```text
输入：MK、UTF-8 明文字节、AAD
  ↓
操作系统随机源 OsRng 生成 24 字节 nonce
  ↓
XChaCha20 根据 MK 和 nonce 产生密钥流
  ↓
密钥流与明文字节逐字节异或，得到加密后的内容
  ↓
Poly1305 根据密钥、AAD 和加密后的内容生成 16 字节 tag
  ↓
拼接 nonce ‖ ciphertext ‖ tag
```

这里最后一行使用了第 2 节已经定义过的简写。拼接完成后，程序才会使用 base64url 把它转换成适合 Markdown 保存的文本。

#### 解密正文时发生什么

```text
拆出 24 字节 nonce、加密后的内容和 16 字节 tag
  ↓
使用同一把 MK 和同一份 AAD 验证 tag
  ├ 校验失败：返回“损坏或被篡改”，不输出明文
  └ 校验成功：继续解密
  ↓
XChaCha20 还原明文字节
  ↓
按 UTF-8 还原文字
```

密钥不一致、随机数变化、密文变化、tag 变化或 AAD 变化，都会导致解密无法成功。程序不会返回部分明文，也不会尝试猜测或修复。

#### 固定开销

XChaCha20 加密后的内容与明文字节长度相同，额外增加的是 24 字节 nonce 和 16 字节 tag：

```text
二进制加密包长度 = 明文字节数 + 24 + 16
```

所以每次加密固定增加 40 字节，再加上 base64url 文本表示产生的长度增长。

例如 MK 本身是 32 字节，一个 slot 中被包裹 MK 的二进制长度就是：

```text
24 + 32 + 16 = 72 字节
```

#### 同一算法的两种用途

| 用途 | 使用的秘密密钥 | 被加密的数据 | 结果保存在哪里 |
| --- | --- | --- | --- |
| 包裹 MK | 由口令或恢复码派生的 KEK | 32 字节 MK | `vault.json` 的 `wrapped` |
| 加密笔记 | 工作区 MK | 用户内容的 UTF-8 字节 | Markdown 的 secret 密文主体 |

#### 为什么使用 24 字节 nonce

同一把密钥绝不能故意重复使用 nonce。XChaCha20-Poly1305 使用 24 字节 nonce，随机空间非常大，因此每台设备都可以独立生成 nonce，而不需要在 Git 中维护一个全局计数器。

这适合多设备同步：两台设备可以各自重新加密，不需要先询问另一台设备“上一个 nonce 用到了多少”。当前实现每次调用加密函数都会重新使用操作系统随机源生成 nonce。

补充理解名称中的“X”：XChaCha20 会先用 nonce 的前 16 字节，通过一个名为 HChaCha20 的内部步骤派生一次性子密钥，再结合剩余部分运行 ChaCha20。这些内部运算全部由 Rust 的 `chacha20poly1305` 库完成，普通使用和阅读后续章节不需要掌握。

## 7. secret 格式、ID 与 AAD

上一节提到 AAD。理解它之前，先看一个 secret 自己声明了哪些信息。

### 7.1 两种 Markdown 形态

围栏块适合多行内容：

````markdown
```secret {v=1, key=k1, id=b0e08703dbc4ccbc2}
9EhLEDOBweDbCawtEHFT3ZmBbtKIPlSPLuTU6Q7v_0Cq6fPVfoib94BTnHFhhNALpF1mcET4HQ
```
````

围栏块的 base64url 密文每 96 个字符折行。解密前会移除空白，所以折行只影响排版和 Git diff。

行内形态适合一句话中的短内容：

```markdown
服务器口令是 `secret {v=1, key=k1, id=b7c1f2a93e85d40b} sT3nQx_Ab`，请勿公开。
```

行内密文不折行。两种形态使用相同属性、相同 AAD 和相同加密包，因此保持属性不变时，可以只改 Markdown 外形而不重新加密。

### 7.2 三个核心属性

| 属性 | 当前示例 | 作用 |
| --- | --- | --- |
| `v` | `1` | 加密格式版本 |
| `key` | `k1` | 指明使用哪一把工作区主密钥 |
| `id` | `b0e08703dbc4ccbc2` | 标识这一段 secret |

`key` 和 `id` 必须以字母或 `_` 开头，后面只能包含字母、数字、 `_` 或 `-`。

新建 secret 时，前端使用系统安全随机源（Web Crypto）生成 8 字节，也就是 64 位随机 ID，再加一个字母 `b`：

```text
b + 16 位十六进制字符
```

旧版本生成的短 ID 仍然可以解析和解密，不需要迁移。

ID 不是密钥，也不需要保密。它用于参与防篡改校验和帮助前端定位内容。系统没有全局数据库为 ID 做唯一性约束，因此手工编辑源码时不应主动复用 ID。

### 7.3 为什么只校验密文还不够

假设攻击者没有修改密文本身，只把它从：

```text
id=A
```

移动到：

```text
id=B
```

如果 `id` 不参与校验，程序无法发现这段密文换了身份。因此加密时还会把 `v`、`key`、`id` 作为“附加认证数据”一起计算 tag。

附加认证数据的英文是 Additional Authenticated Data，简称 **AAD**。它的特点是：

- AAD 自己不加密，任何人都能看到；
- AAD 不放进加密后的正文；
- AAD 会参与 16 字节 tag 的计算；
- 解密时必须提供完全相同的 AAD。

当前规范化形式是：

```text
v=1|key=k1|id=b0e08703dbc4ccbc2
```

### 7.4 为什么要规范化

下面两行表达相同属性：

```text
secret {v=1,key=k1,id=b0e08703dbc4ccbc2}
secret { v = 1, key = k1, id = b0e08703dbc4ccbc2 }
```

如果直接把原始文本作为 AAD，多输入一个空格就会导致解密失败。因此前端和 Rust 都先解析属性值，再按固定顺序重新拼成 AAD。

### 7.5 AAD 带来的实际行为

- 只复制 secret 的密文主体，再改成另一个 ID：校验失败；
- 修改 `key`：找不到对应 MK，或校验失败；
- 修改 `v`：当前实现只支持 `v=1`，其他版本会在解密前被拒绝；
- 重命名或移动笔记：仍能解密，因为文件路径不在 AAD 中；
- 在块与行内形态之间转换：保持三项属性即可解密。

如果把整个 secret 连同原 ID 一起复制，AAD 仍然相同，副本可以解密。AAD 是防篡改机制，不是禁止复制机制。

未知属性会被解析器保留，但当前不进入 AAD。未来若增加 `hint=` 等展示属性，不能把它们误认为受密码学保护。

## 8. 口令有效期实际控制什么

设置中的“口令有效期”更准确地说，是**MK 可以在 Rust 内存中保留多久**。

### 8.1 有效期从输入口令时开始

默认有效期是 15 分钟，从口令或恢复码成功解锁的那一刻开始计算。

中间进行以下操作都不会自动续期：

- 加密；
- 解密；
- 保存；
- 批量保存；
- 查询状态。

可选设置：

| 设置 | Rust 行为 |
| --- | --- |
| 立即过期（`-1`） | 完成当前这次使用 MK 的命令后立即清除 |
| 1 / 5 / 15 / 30 / 60 分钟 | 从成功输入口令的时刻计算固定截止时间 |
| 从不过期（`0`） | 不按时间清除，仍可被手动上锁、切换工作区或退出应用清除 |

修改有效期不会重置起点。例如已经解锁 10 分钟，再把 15 分钟改成 30 分钟，新的截止时间仍是最初解锁后的第 30 分钟，而不是修改设置后的第 30 分钟。

### 8.2 Rust 主动清理 MK

应用启动时只创建一个名为 `vault-expiry` 的 Rust 后台线程：

```text
成功解锁或修改有效期
  ↓ 唤醒后台线程
线程计算离截止时间还有多久
  ↓ 使用 Rust 的等待/唤醒机制休眠，不轮询
到达截止时间
  ↓
清空 MK，并尽可能把对应内存字节覆写为 0（代码中称为 zeroize）
```

它不是每次加密或解密都创建一个新线程，也不会随着操作次数积累定时任务。

所有使用 MK 的 Rust 命令在开始前还会复查是否过期。后台线程负责主动清理，命令入口复查属于第二道保护。

设置界面的倒计时只是显示。前端每秒更新“距离口令失效还有多少分钟”，到零后重新询问 Rust；真正决定 MK 是否有效的是 Rust。

### 8.3 立即过期为什么在操作后清理

如果在操作前清理，用户刚输入口令，MK 就会在第一次解密前消失。因此立即过期的顺序是：

```text
输入口令并取得 MK
  ↓
完成一次加密、批量加密或解密
  ↓
立即清除 MK
```

同一次保存中的多个脏 secret 会合并为一个批量加密命令，所以一次保存只需要输入一次口令。

## 9. 明文在哪里，保存时又发生什么

### 9.1 外层编辑器始终保留 secret 密文

用户点击 `🔒` 后，Rust 解密出明文，并通过前后端通信通道（Tauri IPC）返回前端。明文会存在于：

- Rust 解密过程中的临时缓冲；
- Tauri IPC 数据；
- 前端 `useVaultStore`；
- secret 内部的嵌套编辑器。

明文不会因为“展开查看”而替换外层 Markdown。主编辑器、自动保存、主编辑器 undo 栈和 Git 仍然看到 secret 密文。

工作区 MK 与明文不同：MK 始终留在 Rust，不会通过 IPC 返回给前端页面（WebView）。

### 9.2 `saved` 和 `draft`

前端为已展开 secret 记住三个值：

| 值 | 含义 |
| --- | --- |
| `body` | 这份明文来自哪一段密文 |
| `saved` | 当前密文解开后的原始明文 |
| `draft` | 用户现在正在编辑的明文 |

只有 `draft` 与 `saved` 不同时，才需要重新加密。

### 9.3 未修改就不重新加密

每次加密都会产生新 nonce，因此即使明文没变，重新加密后的文本也会变化。

如果每次保存都重新加密，用户只是打开并保存笔记也会得到 Git diff；两台设备还会制造无意义冲突。因此保存规则是：

```text
draft 与 saved 相同
  → 保留原密文，不调用 Rust

draft 与 saved 不同
  → 使用 MK 生成新密文，整体替换原 secret
```

一次保存中的所有脏块和行内 secret 会通过 `secret_encrypt_batch` 一起加密。要么全部成功后统一写回，要么不写入部分结果。

### 9.4 什么时候可以弹口令框

| 时机 | 是否主动要求口令 | 行为 |
| --- | --- | --- |
| 嵌套编辑器失焦 | 否 | 有 MK 就写回；没有则保留内存草稿 |
| 保存笔记 | 是 | 必要时重新解锁并批量写回 |
| 切换标签或笔记 | 是 | 卸载编辑器前尽量写回 |
| 切换视图模式 | 是 | 切到源码前尽量让密文对应最新草稿 |
| 点击 `🔑` 收起 | 是 | 改过的内容先写回，没改的直接收起 |
| 立即上锁 | 是 | 主窗口先尝试写回，再清除 MK |

如果用户取消输入口令，未写回的草稿不会被静默丢弃。

项目不提供“一键把 secret 转回外层明文”的命令。确实需要取消加密时，可以从嵌套编辑器复制内容，再明确删除原 secret，避免一次误触就让明文进入自动保存和 Git。

## 10. “收起内容”“MK 过期”和“立即上锁”不是一件事

这是当前交互里最容易混淆的地方。

| 动作或状态 | Rust 中的 MK | 屏幕上的明文 | 未保存草稿 |
| --- | --- | --- | --- |
| 点击某一处的 `🔑` | 保留 | 只收起这一处 | 先写回；取消或失败则不收起 |
| MK 到达有效期 | 清除 | **已经展开的内容继续显示** | 保留，下次保存重新要求口令 |
| 设置中“立即上锁” | 清除 | 已安全写回的内容收起 | 无法写回的草稿继续保留，避免丢字 |
| 关闭或切换笔记 | 保留当前 vault 会话 | 已安全写回的该笔记内容收起 | 切换前尝试写回，失败的草稿不静默丢失 |
| 切换工作区 | 清除 | 清除旧工作区显示缓存 | 不把旧 vault 状态带到新工作区 |

为什么 MK 过期后不立刻隐藏明文？

因为“立即过期”模式会在一次解密后立刻删除 MK。如果“没有 MK”自动等于“隐藏明文”，内容会刚出现就消失；正在编辑但还未写回的文字也可能被一起丢弃。

因此：

> MK 是否存在，决定还能不能进行新的密码学操作；内容是否收起，由用户上锁、关闭笔记等显式动作决定。

## 11. 在编辑器里如何显示和保护

### 11.1 两种显示形态

| 状态 | 围栏块 | 行内内容 |
| --- | --- | --- |
| 已上锁 | `🔒 加密内容` | `🔒 •••••` |
| 解密中 | `🔒` 与进度提示 | `🔒 解密中…` |
| 已解密 | `🔑` 与多行嵌套编辑器 | `🔑` 与单行嵌套编辑器 |
| 版本过高 | 保留密文并提示升级 | 显示版本提示 |
| 无法解密 | `⚠️` 与错误说明 | `⚠️ 无法解密` |

锁和钥匙本身就是操作入口：点击 `🔒` 解密，点击 `🔑` 写回并收起。块和行内形态使用同一套悬停提示文案。

### 11.2 三种视图模式

| 模式 | 围栏块 | 行内内容 |
| --- | --- | --- |
| 实时预览 | 可解密、可编辑 | 可解密、可编辑 |
| 预览（只读） | 可解密，不可编辑 | 可解密，不可编辑 |
| 源码 | 原始围栏、属性和密文 | 原始反引号、属性和密文 |

行内嵌套编辑器会阻止 Enter，因为行内 secret 不能跨行。围栏块的嵌套编辑器支持多行 Markdown，但不会运行其中的代码，也不会继续嵌套交互组件。

### 11.3 为什么密文不会被光标啃掉一部分

实时预览中的卡片和行内 chip 只是视觉替换，底层仍然是外层文档中的密文。实现用两层保护防止误改：

1. **原子范围**：方向键一次跨过整个 secret，选择吸附到边界；
2. **事务守卫**：一次编辑只能完整保留 secret，或整体替换、整体删除。

围栏块还必须继续独占完整行。粘贴、拖放、输入法或删除相邻换行如果会留下半个 secret，整笔编辑会被拒绝。

围栏块需要连续按两次删除键：第一次高亮待删除块，第二次删除。行内 chip 像一个普通 token，一次退格即可整体删除。

源码模式不安装这些守卫。用户可以手工修复密文，也可以把它改坏、删除，甚至替换成明文；明文随后会像普通 Markdown 一样写入磁盘和 Git。

## 12. 错误发生时怎样保护原文

| 错误 | 用户能理解的含义 | 程序行为 |
| --- | --- | --- |
| `locked` | MK 不在 Rust 内存中或已过期 | 重新请求口令，不修改密文 |
| `unknown_key` | secret 指向的主密钥当前不存在 | 提示由其他密钥加密，不修改密文 |
| `tampered` | 防篡改校验失败 | 提示损坏或被篡改，不修改密文 |
| `bad_format` | 属性、标识符、base64/base64url 或 UTF-8 无法识别 | 降级显示或提示格式错误，保留原文 |
| `wrong_secret` | 口令和恢复码 slot 都打不开 | 提示输入不正确 |
| `not_initialized` | 工作区没有 `vault.json` | 引导首次设置 |
| `already_initialized` | 已有 vault 又尝试初始化 | 拒绝覆盖 |

格式解析遵循一个原则：

> 看不懂就保持原样，不替用户猜测或自动修复密文。

具体表现：

- 属性顺序和空格可以变化；
- `v`、`key`、`id` 必须各出现一次；
- 未知属性会被保留；
- 无法识别的围栏按普通代码块显示；
- 无法识别的行内 secret 按普通行内代码显示；
- 版本过高、密钥未知或校验失败时，原始 Markdown 一个字节都不改。

## 13. 修改口令与多设备同步

### 13.1 修改口令

修改口令只会重新包裹 MK：

```text
当前口令或恢复码
  ↓ 取得 MK
新口令
  ↓ Argon2id 生成新 KEK
使用新 KEK 重新加密同一把 MK
  ↓
更新 vault.json 的口令 slot
```

笔记密文不变，已经解锁的当前会话也不会因此立即失效。

### 13.2 重置 MK

“修改口令”不改变 MK；“重置 MK”则会生成全新的随机 MK，并重新加密当前工作区所有 Markdown 中的围栏和行内 secret。主口令保持不变，迁移完成后旧恢复码失效，界面会只显示一次新恢复码。

迁移首先扫描并验证全部密文。只要有一处格式错误、密钥未知或校验失败，就不修改任何文件。通过预检后，`vault.json` 会短暂保留新旧两组密钥 slot：

```text
写入新旧 MK 共存的过渡 vault
  ↓
逐文件原子替换 secret 密文
  ↓
所有文件完成后删除旧 MK slot
```

如果进程在途中中断，过渡 vault 仍能同时打开已迁移和未迁移的密文。设置页会显示“继续完成 MK 重置”，再次输入当前主口令即可续跑。迁移会改写密文，因此会正常产生 Git 差异。

### 13.3 换一台设备

另一台设备需要同时取得：

- Markdown 中的 secret 密文；
- `.ideanote/vault.json` 中被包裹的 MK。

然后输入同一口令：

```text
口令 + vault.json 中的盐和参数
  ↓ Argon2id
得到相同 KEK
  ↓ 解开 slot
得到相同 MK
  ↓
解密笔记内容
```

设备之间没有直接传输明文 MK，但 `vault.json` 中被加密包裹的 MK 必须随仓库同步。

## 14. 其他功能会看到什么

没有明确解密操作的功能只读取外层文档，因此看到的是密文，而不是嵌套编辑器中的明文。

| 功能 | 当前行为 |
| --- | --- |
| 保存、Git、主编辑器 undo | 处理外层 secret 密文 |
| AI 读取笔记 | 读取外层文档，因此得到密文 |
| 全文搜索 | 扫描磁盘，可能命中 base64url 噪声，但不会得到明文 |
| 大纲 | 跳过围栏内容；标题中的行内 secret 显示为 `🔒` |
| 代码运行 | `secret` 被硬排除，不显示运行按钮，也不送入解释器 |
| 导出和打印 | 当前可能显示原始密文，不会自动解密 |

搜索跳过密文、AI 显示可读占位和导出占位仍可继续完善，但不应该通过把明文写进外层文档来实现。

## 15. 安全边界：它能防什么，不能防什么

### 15.1 主要防护目标

笔记加密主要防护静态数据泄漏：

- 仓库或 Git 历史泄漏；
- 云同步服务读取文件；
- 未解锁时直接打开 Markdown；
- 设备丢失后从工作区复制笔记。

### 15.2 弱口令仍可能被离线猜中

`vault.json` 会随仓库同步，因此拿到仓库的攻击者可以反复离线尝试口令。Argon2id 会增加每次尝试的内存和计算成本，但无法把 `123456` 变成强口令。

项目当前不做口令复杂度校验，这是避免复杂规则增加遗忘风险的产品取舍，不代表弱口令安全。

### 15.3 解锁期间内存中存在敏感数据

- MK 位于 Rust `VaultState` 的可清零字节缓冲中，代码类型为 `Zeroizing<[u8; 32]>`；
- KEK 只在派生和解包期间短暂存在；
- 用户输入的口令或恢复码会经过 UI、Tauri IPC 和 Rust 字符串；
- 解密明文会经过 Rust 临时缓冲、IPC、JavaScript 字符串、状态 store 和嵌套编辑器。

JavaScript 字符串和部分 Rust 字符串无法保证原地擦除。因此本功能不防本机恶意程序、调试器、键盘记录、内存转储、swap、休眠镜像或崩溃报告。

`zeroize` 可以降低 MK 和 KEK 字节缓冲残留的风险，但不是物理内存清除保证。

### 15.4 元数据和长度不会隐藏

攻击者仍然可以看到：

- 哪些笔记包含 secret；
- 每篇有多少段；
- 每段密文大致多长；
- `v`、`key`、`id`；
- vault 有多少 slot、创建时间和 Argon2id 参数。

加密保护内容本身，不提供整篇文件隐写、流量填充或长度隐藏。

### 15.5 应用写盘保证不等于操作系统保证

正常的 secret 编辑流程不会把已展开明文写进外层 Markdown。但操作系统可能产生 swap、休眠镜像或崩溃转储，因此不能承诺任何物理介质上从未出现过明文字节。

## 16. 日常使用建议

### 16.1 第一次使用

1. 为工作区设置口令；
2. 把一次性恢复码保存到密码管理器或纸上；
3. 确认 `.ideanote/vault.json` 没有被 `.gitignore` 排除；
4. 将 `vault.json` 和加密笔记一起备份或提交。

### 16.2 查看和编辑

1. 选中文字，选择围栏加密或行内加密；
2. 点击 `🔒`，必要时输入口令或恢复码；
3. 在 `🔑` 旁的嵌套编辑器中编辑；
4. 正常保存笔记；
5. 点击 `🔑` 收起单项，或在设置中立即上锁并清理 MK。

### 16.3 必须记住的恢复条件

要解密笔记，必须同时拥有：

```text
secret 密文 + vault.json + 正确口令或恢复码
```

缺少其中任何一项，都无法得到原文。

## 18. 最后分三步回顾

第一步只负责取得 MK：

```text
口令或恢复码
  ↓ Argon2id
KEK
  ↓ 解开 vault slot
MK
```

拿到 MK 后，加密笔记：

```text
明文文字
  ↓ UTF-8
明文字节
  ↓ 使用 MK 加密
nonce ‖ ciphertext ‖ tag
  ↓ base64url
Markdown 中的 secret 密文文本
```

拿到 MK 后，解密笔记：

```text
Markdown 中的 secret 密文文本
  ↓ base64url 解码
nonce ‖ ciphertext ‖ tag
  ↓ 使用 MK 校验并解密
明文字节
  ↓ UTF-8
明文文字
```

# 笔记分块加密方案

本文记录 Idea Note 的分块加密功能：在 Markdown 笔记里加密任意一段内容，密文随现有 Git 同步到每一台设备，输入同一口令即可打开。**磁盘上任何时刻都不出现明文。**

- 算法：XChaCha20-Poly1305（内容）+ Argon2id（口令派生）
- 加解密全部在 Rust 侧完成，主密钥从不进入 WebView
- 实现分三阶段，本文同时记录已完成部分与后续计划

## 1. 设计前提

以下四条是拍板的前提，后面所有实现都建立在它们之上。

| 前提 | 决定 | 理由 |
| :--- | :--- | :--- |
| 编辑模型 | 嵌套子编辑器 | 主文档缓冲区里永远是密文，明文只活在 widget 内挂载的小 EditorView 和 Rust 内存里。自动保存、崩溃、undo 栈、Git 历史天然不沾明文 |
| vault 存放 | 入库同步 | `<工作区>/.ideanote/vault.json` 随仓库提交，换设备只需输口令 |
| 口令强度 | **不做校验** | 任意长度、任意内容都接受。忘记口令是**必然**的数据丢失，弱口令只是**可能**被攻破——而复杂度规则正是让人记不住的原因 |
| 密钥寿命 | 闲置 15 分钟 | 滑动过期，可设立即过期 / 1/5/15/30/60 分钟 / 从不。在 Rust 的每个使用点强制，不靠 UI 定时器 |

## 2. 密钥体系

这是多端能跑通的核心。**双层密钥**：

```
口令 ──Argon2id(salt, m=64MB, t=3)──> KEK ──解包──> MK ──加解密──> 各个 secret 块
```

- **MK（主密钥）**：工作区级随机 32 字节，真正加密内容。**它是随机生成的，不是从口令算出来的**。
- **KEK**：由口令派生，只用来包裹 MK。

这样拆开有三个好处：

1. **改口令只需重新包裹 MK，不用重新加密所有笔记**。否则改一次口令就是整仓 diff，其他设备全部要合并。
2. 多端只要输入同一口令即可，不需要在设备间传输任何密钥材料。
3. 类 LUKS 的多 slot——口令 slot、恢复码 slot，以后可加设备 slot。

### 2.1 三个密钥各自的寿命

| 密钥 | 怎么来 | 活多久 | 落不落盘 |
| :--- | :--- | :--- | :--- |
| KEK | Argon2id(口令, salt) | 解锁那一瞬间，用完立刻 zeroize | 否 |
| MK | 解包 vault slot 得到 | 解锁 → 上锁期间常驻 Rust 内存 | 只以「被 KEK 包裹」的形态存在 vault.json |
| 内容密文 | MK 加密每个块 | 永久 | 是，就在 .md 里 |

### 2.2 为什么是 XChaCha20 而不是 AES-GCM

关键是 nonce 宽度。AES-GCM 是 12 字节 nonce，随机取的话按生日界约 2³² 次加密就开始有碰撞风险；而本场景下每次保存每个块都会重新加密，一个长期使用的工作区跑出几百万次加密完全可能。一旦 nonce 复用，GCM 会**直接泄漏明文异或值并让认证密钥可被恢复**，是灾难级失效。

XChaCha20 的 24 字节 nonce 让随机取值的碰撞概率彻底可忽略，不需要维护任何计数器状态——而计数器状态在多端同步场景下根本没法可靠维护（两台机器各自加密，谁也不知道对方用到第几号）。

### 2.3 Argon2id 不是加密算法

它是**密钥派生函数（KDF）**，单向不可逆，没有"解密"这个操作。职责分工：

> **Argon2id 扛离线爆破 → XChaCha20-Poly1305(KEK) 保护 MK → XChaCha20-Poly1305(MK) 保护笔记正文**

选它而不是 SHA-256，是因为 SHA 太快（GPU 每秒几百亿次）。Argon2id 的 `m=64MB, t=3` 意味着每算一次口令都必须实打实占用 64MB 内存并反复读写 3 轮，GPU 的并行度被显存卡死，把爆破速度压低八个数量级。

盐**不是秘密**，明文存在 vault.json 里，而且**必须存**——换设备时要靠它算出同一个 KEK。它的作用是破坏彩虹表和批量攻击。

## 3. 数据格式

两个格式一旦发版就不能随意改。都带版本号，将来演进靠版本号分支而不是原地改语义。

### 3.1 笔记里的 secret 块

沿用项目既有的 fence attribute 约定（`fenceAttrs.ts` 里 ` ```python {in=loan, out=table} ` 那一套）：元数据写在 `{}` 里，块体只放密文。

````markdown
```secret {v=1, key=k1, id=b9f3a2c}
<base64url( nonce24 ‖ ciphertext ‖ tag16 )，按 96 字符折行>
```
````

- `v=1` 格式版本 · `key=k1` 密钥 id（支持轮换） · `id=b9f3a2c` 块 id
- 块 id **必须字母开头**：既有的 `IDENT = /^[A-Za-z_][A-Za-z0-9_-]*$/` 会拒绝 `9f3a2c` 这种数字开头的值。用 `b` + 3 字节随机 hex，共 7 字符
- nonce 不放属性里，和密文、tag 一起打包进块体——这是 AEAD 的标准封装
- 密文按 96 字符折行；**行级 diff 让 Git 冲突退化成整块二选一**，不会产出半截损坏密文
- 用围栏块而非行内标记：任何 Markdown 渲染器都能降级成一段普通代码块，不破坏文档结构

### 3.2 AAD 从规范化形式重建

```
v=1|key=k1|id=b9f3a2c
```

属性行允许 `{v=1,key=k1}` 和 `{ v = 1 , key = k1 }` 这类空格差异，所以 AAD **必须由解析后的值重新拼装**，而不能直接取 fence 行的原始字符串——否则用户手滑多打一个空格，整块就永久解不开了。

只有 `v` / `key` / `id` 三个字段进 AAD。将来若加 `hint=` 之类的展示用属性，它们**不受认证保护**（可被篡改而不触发 tag 失败）。

AAD 把密文钉死在这个 blockId 上：把密文整段复制到另一个块 id 下，tag 校验就会失败。**不绑文件路径**，否则重命名笔记就全解不开了。

### 3.3 工作区的 vault.json

`<工作区>/.ideanote/vault.json`：

```json
{
  "version": 1,
  "activeKeyId": "k1",
  "slots": [
    {
      "id": "s1", "type": "password", "label": "主口令",
      "keyId": "k1",
      "kdf": { "alg": "argon2id", "m": 65536, "t": 3, "p": 1, "salt": "<b64 16B>" },
      "wrapped": "<b64: nonce24 ‖ wrappedMK ‖ tag16>",
      "createdAt": 1756500000000
    },
    { "id": "s2", "type": "recovery", "...": "同结构，wrapped 的是同一个 MK" }
  ]
}
```

文件里没有任何明文密钥。抗爆破完全压在 Argon2id 成本参数上。

> **这个文件必须提交到仓库**，否则其他设备打不开加密内容。注意 `.gitignore` 里的 `.idea` 只匹配同名目录，不会波及 `.ideanote`。

## 4. 加密流程

### 4.1 首次初始化（每个工作区一次）

```
① salt      = OsRng(16B)
② KEK       = Argon2id(password, salt, m=64MB, t=3, p=1) → 32B
③ MK        = OsRng(32B)                    ← 真正的内容密钥，此刻诞生
④ n_wrap    = OsRng(24B)
⑤ wrapped   = XChaCha20Poly1305(KEK).encrypt(n_wrap, MK, aad=slot 元数据)
⑥ 写 .ideanote/vault.json
⑦ 生成恢复码 R = base32(OsRng(15B))，重复 ①②④⑤ 造出第二个 slot
⑧ zeroize(password, KEK)；MK 留在 State<Mutex<VaultState>> 里 → 状态变为「已解锁」
```

**恢复码是唯一的安全网。** 初始化时强制用户勾选确认已保存，不勾不让完成。

### 4.2 加密一段选中内容

```
前端                                  Rust (crypto.rs)
─────────────────────────────────────────────────────────
检查 vault 状态（未初始化 → 引导设口令；已锁定 → 弹解锁框）
选区扩展到整行（围栏必须独占一行）
blockId = "b" + hex(OsRng(3B))
invoke secret_encrypt ────────────→  ① MK 取不到 → Err("locked")
                                     ② nonce = OsRng(24B)
                                     ③ aad = "v=1|key=k1|id=b9f3a2c"
                                     ④ ct‖tag = XChaCha20Poly1305(MK)
                                                 .encrypt(nonce, plaintext, aad)
                                     ⑤ 返回 base64url(nonce ‖ ct ‖ tag)
      body ←──────────────────────────
把选区替换为 ```secret 围栏块
```

### 4.3 保存时的「未变不重加密」

这一步不是优化，是**正确性要求**。少了它每次保存 nonce 都变，两端各保存一次必冲突，而冲突的还是不可读的密文。

```
嵌套编辑器失焦 / 文档保存 / 切换标签 / 切换视图模式
  ↓
比较当前明文与「上次加密时的明文」
  ├ 相同 → 沿用旧密文，不调 Rust，文档零改动，git 零 diff
  └ 不同 → 重新加密（新 nonce）→ 替换该行
  ↓
主文档 writeFile —— 写出去的永远是密文
```

> **验收标准**：打开笔记、解锁、什么都不改、保存 → `git diff` 必须为空。

所有待加密的块通过 **`secret_encrypt_batch` 一次命令**完成，不是逐块调用。一次保存对用户是一个操作，对密钥也必须是一个操作——否则在「立即过期」下，一次 Ctrl+S 会弹出 N 次口令框。要么全部加密成功，要么一个都不写：半写的笔记没法判断哪半是新的。

### 4.4 什么时候可以弹口令框

密钥可能在编辑期间过期，此时 flush 需要重新拿到口令。但不是每次 flush 都该打断用户：

| 时机 | 允许弹框 | 理由 |
| :--- | :--- | :--- |
| 嵌套编辑器失焦 | 否 | 顺带的同步，草稿留在内存里是安全的 |
| 保存 / 切换笔记 / 切换视图模式 / 上锁 | 是 | 用户的明确动作 |

失焦也弹框的话，「立即过期」下光标一离开块就要输口令，功能直接不可用。

被挡住的 flush 会返回 `blocked` 计数，保存路径据此弹 toast，**不会静默失败**。

### 4.5 口令过期不影响已经解密的明文

这是最容易写错的一条。**「vault 已上锁」和「这个块该不该隐藏」是两件事**，把它们当成一件会直接破坏立即过期模式：那里密钥用完即弃，于是刚解密的块会在明文出现后一瞬间被清掉，用户一眼都看不到。

规则是：

> **口令过期只影响「能不能写」，不影响「能不能看」。**

| 情况 | 行为 |
| :--- | :--- |
| 口令过期，明文**没改过** | 继续显示；点「上锁」直接收起，**不需要输口令** |
| 口令过期，明文**改过了** | 继续显示，卡片标注「保存这段改动时需要重新输入」；保存或上锁时才问口令 |
| 立即过期模式 | 同上。解密后密钥立刻丢弃，但已展开的块照常显示 |

因此**状态刷新（`refresh`）不再有清理明文的副作用**，隐藏明文只由显式动作驱动：

| 动作 | 效果 |
| :--- | :--- |
| 点卡片上的「上锁」 | 收起这一个块；改过的先加密（会问口令），用户取消则保留明文不丢 |
| 关闭 / 切换笔记 | `sealClean(path)`，只丢已加密回文档的那部分 |
| 手动「立即上锁」/ 关闭工程 | 同上，范围是全部笔记 |
| 切换工作区 | 全部丢弃——那些明文属于另一个 vault |

**任何路径都不会静默丢掉未加密的编辑**：flush 被挡住时返回 `blocked` 计数，保存路径弹 toast，`sealClean` 与 `keepUnsaved` 都跳过 `draft !== saved` 的条目。

### 4.6 缓存状态可能是陈旧的

前端的 `status` 只在 `refresh()` 跑到时更新，而立即过期模式下 Rust 用完密钥就丢、不通知前端。于是「点解密」时缓存可能仍说「已解锁」，直接调用就会收到 `locked`。

处理方式是**把这个错误当成信号而不是终点**：`decryptBlock` 把 `locked` 原样返回给调用方（不画成错误卡片），`reveal` 收到后重新走一次解锁流程再解密。否则用户会看到一个按了也没用的「重试」按钮。

## 5. 解密流程

### 5.1 解锁 vault

```
用户输入口令 → invoke vault_unlock
  ↓ Rust（在 spawn_blocking 线程池里跑，不阻塞 UI）
for slot in slots:
    KEK = Argon2id(输入, slot.salt, slot.kdf.m/t/p)
    MK? = XChaCha20Poly1305(KEK).decrypt(slot.nonce, slot.wrapped, aad)
    zeroize(KEK)
    if tag 校验通过:            ← Poly1305 tag 就是「口令对不对」的判据，
        记住这个 MK                不需要另存口令 hash
所有 slot 失败 → Err("wrong_secret")   ← 不透露是哪个 slot 差一点
```

口令 slot 和恢复码 slot 在同一个循环里，所以输恢复码走的是完全相同的路径。恢复码在派生前会规范化（去掉分组连字符、转大写）。

### 5.2 解密一个块

**每个块都默认关着，点「解密」才展开，而且一次只展开这一个。**

```
解析 fence 属性 → v / keyId / blockId
  ├ 版本更高        → 「由更高版本创建，请升级」，原文不动
  ├ 属性无法识别    → 降级成普通代码块，原文不动
  └ 用户点击「解密」↓
     ├ 无 MK（未解锁或已过期）→ 先弹口令框
     └ 有 MK → 直接解密
        ↓ Rust
        ① 按 keyId 取 MK（当前 key 或轮换前保留的历史 key）
        │    找不到 → Err("unknown_key")
        ② aad = "v=1|key=…|id=…"   ← 用密文自己声明的值重建
        ③ decrypt → tag 失败 → Err("tampered")
        ↓
     明文进 widget 的子编辑器（不进主文档缓冲区、不进 undo 栈、不进磁盘）
```

三种失败分支的共同处理：**原始密文行一个字节都不改**。解不开就摆在那儿等，绝不删、绝不替换成占位符再保存——一次误判就是永久数据丢失。

### 5.3 换一台设备为什么就能打开

```
设备 B: git pull
  ├ 拿到 note.md      （密文）
  └ 拿到 vault.json   （salt + kdf 参数 + wrapped MK）
用户输入同一口令
  ↓
Argon2id(口令, vault.json 里的 salt 和参数)   ← 都来自文件，不是本机生成
  ↓
得到与设备 A 完全相同的 KEK → 解包出相同的 MK → 所有块正常解密
```

设备间**没有传输过任何密钥材料**，传的只是「被包裹的 MK」和密文。口令始终只在用户脑子里。

## 6. 锁定状态机

| 触发 | 效果 |
| :--- | :--- |
| 点「解密」 | 只展开这一个块 |
| 点「上锁」（卡片上） | 收起这一个块，**密钥保留**，重新展开无需输口令 |
| 关闭 / 切换笔记 | 该笔记所有块重新上锁，密钥保留 |
| 闲置超时（默认 15 分钟） | **密钥清除**，所有块上锁，再看要输口令 |
| 立即过期模式 | 每完成一次用到密钥的操作就清除，等于每次解密都要输口令 |
| 口令过期（任何模式） | **已解密的块保持展开**，明文照常可见，见 §4.5 |
| 右键「立即上锁」/ 关闭工程 | 同上，立即生效 |

每一条都先 flush，任何路径都不会丢掉在块里打的字。

**有密钥 ≠ 全部展开。** 解锁的本意是拿到钥匙，不是把所有抽屉同时拉开。

密钥寿命是**滑动过期**，从最后一次用到密钥（解密或加密某个块）算起，所以连续工作不会被打断，走开才会失效。过期检查**在 Rust 的每个使用点强制**，不靠 JS 定时器——定时器可能被漏掉、被休眠的渲染进程挂起、或者根本不触发，而「密钥过期了」必须是密钥自己的事实。

设置项的编码：`-1` 立即过期、`0` 从不过期、`>0` 分钟数。检查分成两个时机：

- `enforce_ttl()` 跑在使用**之前**，只处理普通 TTL
- `finish_use()` 跑在使用**之后**，立即过期在这里丢密钥，普通 TTL 在这里重置计时

## 7. 各视图模式的行为

| 模式 | 加密块显示 |
| :--- | :--- |
| 实时预览 | 🔒 卡片 / 解密后的嵌套编辑器 |
| 预览（只读） | 🔒 卡片，不可编辑 |
| **源码** | **原始 fence + base64 密文** |

源码模式下可以直接编辑那串 base64。改坏了的话切回预览会显示「已损坏或被篡改」，但原始字节不会被改写，撤销或手工改回去都还能救。

## 8. 泄漏面

解锁后能看到明文的地方**只有实时预览/预览模式下那张卡片里的嵌套编辑器**。应用的其他所有路径拿到的仍是密文——这不是靠拦截，是架构决定的：主文档缓冲区里从头到尾就是密文。

| 路径 | 拿到什么 | 为什么 |
| :--- | :--- | :--- |
| AI 助手 | 密文 | `tools.ts` 读的是 `view.state.doc` |
| 全文搜索 | 密文 | Rust 直接扫磁盘文件 |
| 导出 PDF / 打印 | 密文 | 拿到的是 Markdown 字符串 |
| 大纲 / 侧栏摘要 | 密文 | 同上 |
| 保存 / Git / undo 栈 | 密文 | 主缓冲区从不持有明文 |

因此 P2 的「AI 脱敏」不是在堵漏（漏本来就不存在），剩下的价值是把 base64 噪声换成可读占位符，以及防止模型覆写它读不到的块。

## 10. 已知的坑

按严重程度排序，这些不是「注意事项」，是踩了就要返工的结构性问题。

### 解不开的块，一个字节都不许改

版本过高、keyId 未知、tag 校验失败——三种情况都要把原始密文行原样留在文档里，只在 widget 上显示状态。绝不能替换成占位符再保存，也绝不能在保存时「清理」掉。一次误判就是永久数据丢失，而用户往往在几周后才发现。

### 明文未变就不能重新加密

忘了这条，功能表面上完全正常，但每次保存都会重写所有加密块，两台设备各编辑一次就必然冲突，而冲突的还是不可读的密文——用户根本无从判断该保留哪边。

### vault.json 不能走通用的 Git 冲突策略

现有策略是保留双方冲突标记并完成合并，这在 Markdown 上是对的，在 JSON 上会产出语法错误——而 vault 一坏，工作区里**所有**笔记全部打不开。已做第一道防线：解析失败时明确报错并提示从 Git 历史恢复，绝不当成「还没初始化」而覆写。完整的冲突处理见 P2。

### widget 会被随时重建，明文不能挂在实例上

CodeMirror 重建装饰的时机很多（切标签、改主题、文档变更）。明文必须放在 store 里按 blockId 索引，widget 只是渲染层。

### MK 绝不能出现在任何 IPC 返回值里

一旦 MK 进了 WebView，它就可能进 JS 堆快照、devtools、崩溃报告。自检标准很简单：**任何返回类型里出现 32 字节密钥就是错的**。

### 跑 KDF 的命令必须是 async

Argon2id 要跑 0.3–1 秒，而同步 Tauri 命令执行在主线程上——这段时间窗口完全没有响应，连进度动画都渲染不出来。`vault_init` / `vault_unlock` / `vault_change_password` 都用 `async` + `spawn_blocking`。

### 「立即过期」不能用零长度空闲窗口实现

`enforce_ttl` 跑在使用之前。如果让它处理零秒空闲，密钥会在解锁和第一次解密之间就被清掉，永远用不上。立即过期必须由使用**之后**的 `finish_use` 负责。

同理，立即过期要求「一次用户操作 = 一次命令」，这就是加密必须批量的原因。

### 「密钥没了」不等于「明文该收回」

状态刷新一旦带上「locked 就清明文」的副作用，两种情况都会出事：正在编辑、尚未加密回文档的内容会跟着消失（在块里连续打字超过有效期，字就在眼前没了）；立即过期模式下更彻底——密钥用完即弃使 locked 成为稳态，刚解密的块在明文出现后一瞬间就被清掉。

隐藏明文必须只由显式动作驱动，见 §4.5。

### 上锁必须发生在持有明文的那个窗口

设置窗是独立 webview，它直接调 `vault_lock` 只会丢密钥，拿不到主窗编辑器里尚未加密的草稿。改成设置窗只发 `vault-lock-request` 事件，主窗收到后走 flush → 上锁。

## 12. 明确不保证

这些要写进 UI 和 README，不能只留在文档里。

- **忘记口令且丢失恢复码 = 数据永久丢失。** 没有后门，没有客服找回。
- **不防本机恶意程序。** 解锁期间 MK 在进程内存里，有本机代码执行能力的攻击者可以拿到它。这个功能防的是仓库泄漏、云端同步服务、设备丢失，不防已经攻破本机的对手。
- **不防内存取证。** zeroize 尽力而为，但不能对抗休眠文件、内存转储、swap。另外**明文比 MK 更难擦**：MK 是主动清零的字节数组，明文是 JS 字符串，不可变、由 GC 回收，无法可靠擦除。
- **vault.json 入库意味着可离线爆破，而口令强度不做校验。** Argon2id 把每次猜测的成本抬到约 0.3–1 秒，但一个真正好猜的口令照样会被破。这是明确的取舍。
- **元数据不加密。** 哪篇笔记有加密块、有几块、每块多长，都是公开可见的。
